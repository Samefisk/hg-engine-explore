# Build HeartGold maps without Windows GUIs

As of October 2026, no existing tool gives an agent a headless, macOS-native way to write HeartGold/SoulSilver maps. The community standard is still Pokémon DS Map Studio (PDSMS) for geometry and DSPRE for headers, matrices and events. Both are GUI-only, and both assume Windows for their essential steps: DSPRE is a .NET Framework 4.8 WinForms app, and PDSMS needs Nintendo's proprietary `g3dcvtr.exe` to produce NSBMD. The format knowledge, however, is now good enough to build the pipeline in-house. pret/pokeheartgold gives exact struct layouts and limits, pret/pokeplatinum has the best map and BDHC specification, and DSPRE's C# parsers fill in the HGSS-specific land_data and area-data details. Readers such as uxie (Rust, MIT, `--json`), apicula (Rust, 0BSD) and noclip's NNS_G3D loader can act as independent oracles. The existing P0–P5 plan therefore holds. Four changes follow from the research. First, own every codec and treat outside tools as references or validators, never as the write path. Second, add a warp-graph and budget linter to P2. Third, split P4 so the BDHC generator, which is easy and well documented, ships long before the NSBMD writer, which is the one real unknown. Fourth, prefer the 39 maps pokeheartgold already labels `*_UNUSED` before any header-table expansion. The rest of this report explains each finding, then gives the revised plan.

## The format knowledge exists, but in three sources that must be combined

No single document describes HGSS maps correctly. **pokeheartgold supplies the authoritative structs**: the 24-byte `MapHeader` bitfield, the matrix loader, the zone-event layouts (20-byte BG, 32-byte object, 12-byte warp and 16-byte coord records) and the 540-entry map-ID space ([PHG map_header.h](https://github.com/pret/pokeheartgold/blob/master/include/map_header.h), [PHG map_events_internal.h](https://github.com/pret/pokeheartgold/blob/master/include/map_events_internal.h), [PHG maps.h](https://github.com/pret/pokeheartgold/blob/master/include/constants/maps.h)). It has no decompiled C for the streaming land-data loader, though. The HGSS land_data container therefore has to come from DSPRE. That container holds four u32 section lengths, an **HGSS-only background-sound (BGS) block** marked by `0x1234`, then 2048 bytes of permissions, 48-byte building records, the NSBMD and the BDHC. DSPRE also gives the **8-byte HGSS area-data record**, which carries an indoor/outdoor byte and a light byte ([DSPRE MapFile.cs](https://github.com/DS-Pokemon-Rom-Editor/DSPRE/blob/main/DS_Map/ROMFiles/MapFile.cs), [DSPRE AreaData.cs](https://github.com/DS-Pokemon-Rom-Editor/DSPRE/blob/main/DS_Map/ROMFiles/AreaData.cs)). pokeplatinum's `docs/maps` contributes the BDHC plate/strip model, the 48-byte prop struct, the area-light text format and a graph of how all these files point to each other ([PP file_format_specifications.md](https://github.com/pret/pokeplatinum/blob/main/docs/maps/file_format_specifications.md), [PP bdhc.md](https://github.com/pret/pokeplatinum/blob/main/docs/maps/bdhc.md)). The DS-Pokemon-Hacking wiki is the maintained community layer on top of these: the HGSS file-structure table, mapping FAQs, town-map and headbutt guides ([DSPH generation-iv](https://github.com/DS-Pokemon-Hacking/ds-pokemon-hacking.github.io/tree/main/docs/generation-iv)).

Per-tile permissions are one little-endian u16. **Bits 0–7 hold the behavior, bits 8–14 a 7-bit secondary field, and bit 15 the collision flag.** These are read by three separate ARM9 accessors ([PHG unk_02054648.s](https://github.com/pret/pokeheartgold/blob/master/asm/unk_02054648.s)), and behavior names come from `enum TILE_BEHAVIOR` ([PHG metatile_behavior.h](https://github.com/pret/pokeheartgold/blob/master/include/constants/metatile_behavior.h)). DSPRE's "collision byte 0x80" is simply bit 15 seen from the high byte. A tile can be blocked and still carry a secondary value. Community sources call the secondary field footstep sound ([DSPH mapping FAQs](https://github.com/DS-Pokemon-Hacking/ds-pokemon-hacking.github.io/blob/main/docs/generation-iv/guides/mapping/mapping_faqs.mdx)), but no primary source confirms that meaning.

Three conflicts must be settled by measurement before P1 code is written, not by choosing one source over another. First, **matrix byte 0 is `width` in the HGSS loader but `height` in the Platinum doc** ([PHG map_matrix.c](https://github.com/pret/pokeheartgold/blob/master/src/map_matrix.c), [PP spec](https://github.com/pret/pokeplatinum/blob/main/docs/maps/file_format_specifications.md)). Second, the decomp hard-codes terrain attributes at offset 0x14 ([PHG terrain_attributes.h](https://github.com/pret/pokeheartgold/blob/master/include/terrain_attributes.h)), yet a parse of the 676 vanilla land_data files found **230 with a non-empty BGS payload**, so a codec must honour the BGS length field ([PHG files/a/0/6/5](https://github.com/pret/pokeheartgold/tree/master/files/a/0/6)). Third, PDSMS keeps separate DP and HGSS BDHC writers, and its HGSS writer appears to store the strip scanline as a 16-bit integer, not as fx32 ([PDSMS BdhcWriterHGSS.java](https://github.com/AdAstra-LD/Pokemon-DS-Map-Studio/blob/master/src/main/java/formats/bdhc/BdhcWriterHGSS.java)). The byte-identical vanilla round-trip in P1 is exactly what settles all three.

The hard limits an agent linter can enforce are also known:

|---|---|---|

The vanilla FIELD2 heap size of 0x1C000 ([PHG field_system.c](https://github.com/pret/pokeheartgold/blob/master/src/field_system.c)) does not apply to this repository, because hg-engine has already changed the field heap layout. Heap budgets must be measured on the current ROM.

## Existing editors are references, not pipeline components

DSPRE is the most complete HGSS map-data editor and is very active, but it is the wrong thing to put in an agent pipeline. **v2.3.4 shipped on 2026-10-13 under AGPL-3.0** ([DSPRE releases](https://github.com/DS-Pokemon-Rom-Editor/DSPRE/releases)). The stable app is a .NET Framework 4.8 WinForms program that requires Windows. The experimental `canary-avalonia` build splits out a `net8.0` `DSPRE.Core` library but ships only Linux and Windows assets, and it warns of "missing features, rough edges, and instability" ([DSPRE canary-avalonia](https://github.com/DS-Pokemon-Rom-Editor/DSPRE/releases/tag/canary-avalonia)). There is no CLI or batch mode. hg-engine ROMs have only partial support, with some editors disabled ([DSPRE README](https://github.com/DS-Pokemon-Rom-Editor/DSPRE)). DSPRE also stores BDHC as raw bytes and does not generate it. One detail matters more for this repository: `DSPRE.Core` now has an `HgEngine/` layer of about 87 files, including `HgEngineHeaderEditor.cs`, `HgEngineSyntheticOverlay.cs` and `HgEngineWriteGuard.cs` ([DSPRE feature/avalonia](https://github.com/DS-Pokemon-Rom-Editor/DSPRE/tree/feature/avalonia/DSPRE.Core)). That suggests DSPRE writes hg-engine source files directly. A human using DSPRE on this checkout could collide with agent-generated sources, so the pipeline should detect such writes rather than invite them. DSPRE's real value is its C# parsers and its Dynamic Header Allocation patch tables, which serve as reference implementations.

PDSMS is in a similar position, with one more problem: licensing. **Upstream Trifindo PDSMS has no license file and has not been updated since 2021.** The active AdAstra-LD fork released v2.4 on 2026-09-24, also without a detected license. Its `.pdsmap` files do not open in vanilla PDSMS ([AdAstra-LD PDSMS](https://github.com/AdAstra-LD/Pokemon-DS-Map-Studio)). It is a Java Swing app. Its `main` only opens a file passed as an argument, and it shells out to `wine g3dcvtr.exe` on non-Windows systems ([PDSMS MainFrame.java](https://github.com/Trifindo/Pokemon-DS-Map-Studio/blob/master/src/main/java/editor/MainFrame.java)). Its Java sources are still the clearest working examples of an IMD writer, an HGSS BDHC writer and loader, BDHCAM, backsound, and the `MapBinHGSS` container packer ([PDSMS formats](https://github.com/Trifindo/Pokemon-DS-Map-Studio/tree/master/src/main/java/formats)). Because there is no license, read them to understand behavior, then write original code. Do not copy them.

The remaining editors change nothing in the plan. SDSME is superseded. CDSRE (GPL-3.0) has been dormant since 2024 ([cdsre](https://github.com/team-cosmic/cdsre)). PokEditor and Pokémon Sinjoh Editor edit species and trainer data, not maps ([PokEditor](https://github.com/turtleisaac/PokEditor), [Sinjoh Editor](https://github.com/GreyLily3/Pokemon_Sinjoh_Editor)). **No porymap equivalent exists for Gen 4** ([porymap](https://flathub.org/de/apps/io.github.huderlem.porymap)), and no Gen 4 ROM-hacking or NDS-emulator MCP server was found. mcp-bizhawk and an mGBA MCP server exist, but neither documents DS support ([mcp-bizhawk](https://glama.ai/mcp/servers/igddve8klv)).

## Small libraries and decomp pipelines make useful oracles

uxie is the most agent-shaped artifact in the ecosystem. **uxie 0.9.5 (2026-10-04, MIT, with an LGPL-3.0+ `nitroarc` submodule)** is a Rust library and CLI. Its `header`, `map`, `event`, `encounter` and `symbols` commands accept `--json`, and it reads both DSPRE project folders and the pokeheartgold and pokeplatinum decomps, resolving constants in both directions ([docs.rs uxie](https://docs.rs/crate/uxie/latest)). Its limits are real: HGSS support is "partial", Platinum is primary, and nothing documents write support or matrix, land_data or BDHC handling. It is well suited as a second, independent reader in P1 and P2. If your encoder and uxie's decoder agree on headers and events, the evidence is stronger than a self-round-trip alone, because a self-round-trip can hide a symmetric misunderstanding.

The decomps provide schemas to copy. pokeheartgold already makes zone events editable as **one JSON file per bank, using symbolic script, object and sprite IDs**, compiled through `jsonproc` and mwasm into `zone_event.narc`. It has no binary-to-JSON step ([PHG zone_event.mk](https://github.com/pret/pokeheartgold/blob/master/files/fielddata/eventdata/zone_event.mk), [example 004_D17R1101.json](https://github.com/pret/pokeheartgold/blob/master/files/fielddata/eventdata/zone_event/004_D17R1101.json)). Encounters and headbutt follow the same JSON pattern. pokeplatinum goes further and represents matrices and area data as JSON with symbolic `MAP_HEADER_*` references, converted by `tools/jsoncnv/map_matrix.py`. Land data remains raw `.bin` in both decomps ([PP map_matrix_000.json](https://github.com/pret/pokeplatinum/blob/main/res/field/matrices/map_matrix_000.json), [PP jsoncnv](https://github.com/pret/pokeplatinum/tree/main/tools/jsoncnv)). These schemas are the right spec format for P1. Adopting pokeheartgold's zone-event JSON shape directly means its 491 vanilla event files serve as ready-made golden fixtures. The hg-engine spec can stay compatible with the decomp instead of inventing a parallel dialect.

The HGSS warp randomizer is an unexpected but useful find. **kotlinds/pokemon-map-randomizer (Apache-2.0, Kotlin, CLI, JVM tests)** is a clean-room rewrite of adrienntindall's C++ HGSS warp randomizer. It rewrites warp destinations while keeping every gym and progression gate reachable ([klibs.io](https://klibs.io/project/kotlinds/pokemon-map-randomizer)). The progression-gate model and warp data it inherits are exactly the inputs a static "is this map reachable, and does every warp have a return" check needs. The underlying block-constraint data comes from the original author, whose license is not visible ([hgss-map-randomizer](https://github.com/adrienntindall/hgss-map-randomizer)), so reuse the design and regenerate the data from vanilla events.

For NARC packing and unpacking, the options are generic: ndspy (Python) and pokeplatinum's nitroarc ([ndspy](https://repos.ecosyste.ms/usage/pypi/ndspy)). hg-engine already has its own build-time NARC handling, so this only matters if P1 tools run outside `make`.

## Geometry has one hard gap: an open NSBMD writer

BDHC is no longer a research problem. pokeplatinum documents the format as axis-aligned rectangular plates, each with a plane normal and constant. Height is `-(n_x·x + n_z·z + d)/n_y`. Overlapping plates resolve to the one nearest the object's current height, and an object outside every plate "will behave erratically" ([PP bdhc.md](https://github.com/pret/pokeplatinum/blob/main/docs/maps/bdhc.md), [PP bdhc.c](https://github.com/pret/pokeplatinum/blob/main/src/overlay005/bdhc.c)). A generator that greedily meshes a tile-height grid into plates, dedupes points, normals and constants, and emits sorted strips is a few hundred lines of code. Its correctness can be checked mechanically: every walkable tile must be covered by a plate, total size must fit the buffer, and the output must re-parse identically. That is the kind of proof an agent can produce without images.

NSBMD is the gap. **The only open-source IMD→NSBMD writer found is Ermelber's nitro-g3d-tools `BinaryConverter`**, a C#/.NET Framework 4.7 tool with no license, last pushed in 2020, and with no reports of producing HGSS-loadable maps ([nitro-g3d-tools](https://github.com/Ermelber/nitro-g3d-tools), [BinaryConverter/Program.cs](https://github.com/Ermelber/nitro-g3d-tools/blob/master/BinaryConverter/Program.cs)). Everything else either reads NSBMD or emits IMD for Nintendo's g3dcvtr. The readers are apicula, noclip and DSPRE. The IMD emitters are PDSMS and the NNS Blender plugin ([apicula](https://github.com/scurest/apicula), [nns-blender-plugin](https://github.com/jellees/nns-blender-plugin)). g3dcvtr is a leaked SDK binary that PDSMS forks refuse to redistribute ([AdAstra-LD PDSMS](https://github.com/AdAstra-LD/Pokemon-DS-Map-Studio)). One macOS user reported it running under Wine 9.15 after an older Wine Staging build failed ([gbatemp](https://gbatemp.net/threads/i-cannot-open-g3dcvtr-using-wine-staging-on-mac-help.660311/)). That makes `wine g3dcvtr.exe` a workable local, user-supplied oracle. It is not a component the repository can vendor or rely on in a shared pipeline.

The cleanest long-term route is a purpose-built NSBMD writer for static map chunks: one node, no skinning, a few materials, and **textures external so materials bind by name to the area's `map_tex_set` NSBTX**. That is how vanilla maps work ([PP maps.md](https://github.com/pret/pokeplatinum/blob/main/docs/maps/maps.md), [noclip Scenes_PokemonHGSS.ts](https://github.com/magcius/noclip.website/blob/main/src/nns_g3d/Scenes_PokemonHGSS.ts)). Three readable specs exist: apicula's parser (0BSD, so it can be read and ported freely), noclip's `NNS_G3D.ts` (custom license, so read it but do not copy it), and GBATEK's GX command reference ([noclip nns_g3d](https://github.com/magcius/noclip.website/tree/main/src/nns_g3d), [GBATEK](https://problemkaputt.de/gbatek.htm)). apicula's `info` and `convert -f=glb` give an open, cargo-buildable validator that runs on macOS. Nobody has published such a writer, so this remains the largest risk in the plan. Texture conversion is better served: **ptexconv (BSD-2-Clause, C CLI)** handles every DS texture format headlessly ([ptexconv](https://github.com/Garhoogin/ptexconv)). It does not write the NSBTX container, so that packing step is still custom.

Rendering is the one area where a tempting tool conflicts with this repository's rules. apicula-to-GLB plus `blender --background`, or a port of noclip's HGSS scene loader, can produce top-down map renders. Those are useful for a human reviewer. Image inspection is not an acceptable agent test step here, so renders should be an optional human-review artifact. Structural checks such as plate coverage, permission/BDHC agreement, prop counts and polygon budgets should carry the proof.

## Emulator tests stay on the repository's own melonDS stack

Nothing external improves on what the repository already has. Standalone melonDS 1.x has a GDB stub and multi-instance support. Its Lua scripting PR was dropped over macOS CI problems, and it has no official headless mode ([melonDS releases](https://github.com/melonDS-emu/melonDS/releases), [blocksds #142](https://codeberg.org/blocksds/sdk/issues/142)). BizHawk's melonDS core has Lua, but BizHawk is not officially supported on macOS, and DeSmuME is ruled out by project policy. No public Gen 4 warp-walk or map-test harness exists. The P2 test generator should therefore emit scenarios for the existing shared melonDS tools and memory-backed proof. The assertions are current map ID, player X/Z, loaded event counts and object counts after a scripted walk through each new warp.

## Revised plan

**P0 — Reconciled format spec.** Write one HGSS map spec that cites pokeheartgold for structs, DSPRE for the land_data/BGS and area-data layouts, and pokeplatinum for BDHC and props. Record the three open conflicts (matrix width/height order, BGS-variable attribute offset, HGSS BDHC strip encoding) and the per-map limits table as linter constants. Add a "tables indexed by map ID" inventory now: mapname.bin, encounters, headbutt, `sSpawnMaps`, Pokégear overlay-101 location tables, and the matrix-0 runtime patches. P5 depends on it.

**P1 — Own codecs with byte-identical round-trip.** Implement in-repository codecs for header table, matrix, area data, zone events (in pokeheartgold's JSON shape), level-script headers and the land_data container. In the container, BDHC is parsed structurally, while NSBMD is an opaque blob in this phase. The gate is a byte-identical round-trip of all 676 land_data, 288 matrices, 106 area files and the vanilla events, plus agreement with uxie's JSON on headers and events. This round-trip resolves the P0 conflicts.

**P2 — Data-only edits with static lint and generated melonDS tests.** Edit specs, not binaries. The linter enforces zone-event size < 0x800, hdr < 0x100, the object count against 64 live slots, symbol resolution, warp-anchor validity, warp reciprocity and graph reachability (modeled on the randomizer's gate design), and permission/BDHC consistency. Each change generates memory-backed melonDS scenarios on the existing shared tools. Treat any DSPRE-modified file as foreign input to re-lint.

**P3 — Recompose vanilla chunks and buildings.** Move or duplicate land_data chunks and props between matrices. The linter checks that every chunk's NSBMD materials resolve in the target area's `map_tex_set` and every prop ID exists in the area's `area_build` list, and stays within the 16-block and 225-cell TerrainAttributes limits.

**P4a — Tile-kit → permissions + BDHC (moved earlier).** Build the greedy-mesh BDHC generator and the permission emitter from the tile kit, using vanilla NSBMDs or P3 chunks for visuals. Structural proof is plate coverage of every walkable tile, size under the measured HGSS buffer, and re-parse identity.

**P4b — Open NSBMD writer (isolated research spike).** Write a static-chunk NSBMD writer with external textures, informed by apicula and GBATEK. Validate it with apicula `info`/`convert` and in-game load tests, and use `wine g3dcvtr` only as an optional local comparison when the user supplies the binary. Textures go through ptexconv into a custom NSBTX packer. Offline renders are a human-review artifact only. Keep P4b off the critical path for P5.

**P5 — New maps via unused IDs, then expansion.** First consume pokeheartgold's 39 `*_UNUSED` IDs (for example 8, 82, 105, 128–130, 208–213, 254–264), after checking each one for remaining code references through the P0 inventory ([PHG maps.h](https://github.com/pret/pokeheartgold/blob/master/include/constants/maps.h)). Expand only when they run out. Relocate `sMapHeaders` through hg-engine's own hooks on the `MapHeader_*` getters, and use DSPRE's Dynamic Header Allocation patch, with its 26 HGSS pointer pairs, only as a reference checklist ([DSPRE ToolboxDB.cs](https://github.com/DS-Pokemon-Rom-Editor/DSPRE/blob/main/DS_Map/Resources/ROMToolboxDB/ToolboxDB.cs)). The DSPRE patch's matrix-expansion companion has undocumented limits, so do not adopt it until those immediates are understood.

## Conclusion

The ecosystem is converging on the same split this plan already makes: a text spec as the source of truth, compiled to binaries. Neither pret decomp has yet extended that to land_data geometry. The work that would materially help an agent is therefore owning the codecs and the linter, not adopting a tool. Whoever ships an open NSBMD writer for static map chunks closes the last gap between Gen 4 and the porymap-style workflow Gen 3 has had for years. That gap is narrow enough to scope as a spike rather than a blocker.

The most important re-sequencing is to decouple collision and terrain (BDHC, permissions) from visuals (NSBMD). The first is fully specified and can be proven structurally today. The second is the only part that depends on unproven or proprietary tooling. Treating them as one P4 step would have let the riskiest piece delay P5, the new-map goal, which can proceed on recomposed vanilla visuals.
